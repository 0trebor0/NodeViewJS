NodeViewJS

Desktop apps with Node.js and the system web view

    NodeViewJS

    A lightweight desktop runtime for building small apps with Node.js, plain HTML/CSS/JavaScript, and the operating system's own web view. Windows uses WebView2, macOS uses WKWebView, and Linux uses WebKitGTK.

    MIT Node.js 20+ Windows verified macOS / Linux pending validation v0.1.0 (untagged)

    Your frontend gets a safe window.NodeViewJS bridge; privileged work stays in registered Node.js commands. Raw Node.js APIs such as require() are never exposed to the web view.

    No Chromium bundled

    Apps use the web view already installed on the machine, so packages stay small.

    No local HTTP server

    Packaged HTML loads directly from disk through a private per-WebView mapping.

    Command-gated backend

    The frontend can only call commands you register, each behind a named permission.

    Signed updates

    Ed25519 manifests, HTTPS delivery, transactional install with rollback.

    Platform parity

    Windows is the reference platform and is verified locally. macOS and Linux compile and pass packaging/platform-boundary tests, but several security controls — trusted-document checks, capability lockdown, native IPC limits, package containment, and integrity verification — do not yet have Windows parity. Sections below are marked where a feature is Windows-only.

    No bridge script tag

    Do not add a bridge <script> to your source HTML. NodeViewJS provides window.NodeViewJS automatically. window.NodeView is retained as a compatibility alias; new apps should use window.NodeViewJS.

    5. Run during development

    npm run dev     # runs: nodeviewjs dev app.js
    powershell

    Dev mode enables DevTools and startup timing, and watches the entry file's directory, reloading the web view when frontend .html, .css, or .js files change. Generated folders such as node_modules, build, and .nodeview-webview are ignored.

    • Frontend reloads keep the Node.js backend process running. Restart dev mode after changing backend code.
    • Uncaught backend exceptions and promise rejections print a [NodeViewJS dev] heading with a stack trace.
    • Missing frontend entries fail before a native window opens.
    • Native web view failures show a Windows dialog and write to stderr; packaged apps capture that in resources/<AppName>.log.
    • Packaged Windows apps force DevTools off even if devtools: true is set.

    nodeviewjs dev manages NODEVIEW_DEVTOOLS, NODEVIEW_DEV_WATCH, and NODEVIEW_STARTUP_TIMING internally. Packaged apps ignore inherited values for those development defaults, so launching from a development shell cannot accidentally enable file watching or timing.

    Frontend bridge

    The bridge exposes five methods on window.NodeViewJS.

    MethodBehavior
    invoke(name, payload)Calls a backend command. Returns a promise for the command's return value.
    on(event, handler)Subscribes to a backend event. Registers synchronously and returns an unsubscribe function.
    once(event, handler)Same, fired at most once. Also returns an unsubscribe function.
    off(event, handler)Removes a listener.
    emit(event, payload)Sends a one-way event to the backend.
    ready()Idempotent. Flushes queued events early; not required in the normal case.
    Do not await on() or once()

    They register listeners synchronously and return unsubscribe functions, not promises.

    Calling commands

    try {
  const result = await NodeViewJS.invoke("settings:read", { section: "editor" });
} catch (error) {
  console.error("Command failed:", error);
}
    javascript

    invoke() rejects when the command is unknown, unauthorized, throws, times out, or receives an invalid payload — always handle rejection. An async backend command with no explicit return value resolves to undefined.

    Events

    const unsubscribe = NodeViewJS.on("status:changed", ({ status }) => {
  document.querySelector("#status").textContent = status;
});

NodeViewJS.once("saved", ({ id }) => console.log("Saved", id));

NodeViewJS.emit("page:opened", { page: "home" });

unsubscribe();
    javascript

    emit() is one-way and does not acknowledge handler completion. When the frontend must wait for backend work, use invoke(). For one-way workflows that still need confirmation, have the receiver emit a separate acknowledgement event.

    Readiness and buffering

    Events in both directions are buffered until the frontend bridge is ready. That covers app.emit() before app.run() and NodeViewJS.emit() while the page is still loading. The bridge flushes automatically just after the page's load handlers run, and resets readiness on reload.

    NodeViewJS.on("app:state", renderState);
await NodeViewJS.ready();   // only for advanced startup control
    javascript

    Supported payloads and limits

    Payloads and results support JSON-style data only: null, booleans, finite numbers, strings (including Unicode), arrays, and plain objects.

    Unsupported: functions, symbols, BigInt, NaN, infinity, DOM elements, cyclic objects, class instances, streams, and native Node.js objects. Convert these to plain data first.

    LimitValue
    Message size256 KiB
    Nesting depth32 levels
    Payload nodes10,000
    Command / event name length128 characters
    Pending calls per window64
    Request timeout30 seconds
    Readiness queue per direction1,024 events or 1 MiB per window

    Before transport the bridge creates and revalidates a detached JSON snapshot, so stateful getters cannot change a payload after validation.

    How the bridge is loaded

    During portable packaging, NodeViewJS writes the bridge to resources/app/__nodeview/bridge.js and adds a relative external script reference to every copied .html file. Your source HTML is never changed. This avoids requiring unsafe-inline, so Windows pages can use a policy such as script-src 'self' while the native host limits resources to the app root.

    Node app starts
  -> native window opens
  -> WebView2 is created
  -> packaged HTML file is loaded directly
  -> its embedded NodeViewJS bridge starts during parsing
    text

    This is fast because there is no local HTTP server, the HTML rewrite happens once at packaging time rather than at startup, packaged native startup skips bridge registration, and pages load directly from local files through a private per-WebView mapping.

    Development mode keeps native document-start injection so live reload works without writing generated HTML next to your source. The same bridge stays embedded in the native addon as a fallback.

    Dynamically generated HTML

    Only files copied into the package are prepared. HTML generated after packaging must provide its own frontend bridge if used as a top-level app page.

    App lifecycle

    Call app.run() once after registering commands, plugins, and backend event handlers. It opens the main window and returns true; a secondary launch of a single-instance app returns false after forwarding its arguments. app.quit() closes every window and releases native resources.

    app.show() and app.hide() target the main window. Each AppWindow also provides show(), hide(), reload(), and close().

    Web view profiles, app data, and logs

    appId identifies persistent web view data and defaults to title. Keep it stable across releases so the same profile is reused.

    PlatformProfileBackend log
    Windows%LOCALAPPDATA%\NodeViewJS\<app-id>-<hash>\WebView2%LOCALAPPDATA%\NodeViewJS\Logs\<app-id>-<hash>\backend.log
    macOSApp-support path ending in WebKit~/Library/Logs/NodeViewJS/<app-id>-<hash>/backend.log
    Linux—${XDG_STATE_HOME:-~/.local/state}/nodeviewjs/<app-id>-<hash>/backend.log

    Set NODEVIEW_LOG_PATH to override the log file during debugging or tests. Logs append across launches and rotate to backend.log.1 past the runtime size limit. Existing .nodeview-webview folders are left untouched and can be removed after confirming the new profile works.

    Window options and controls

    transparent: true makes the web view canvas and native client area fully transparent, so transparent page pixels reveal windows behind the app. The standard Windows frame stays visible, partial opacity is unsupported, and the reserved color rgb(1, 0, 1) must not appear in page content — Windows uses it internally as the transparency key.

    closeToHide: true makes the close button hide the window instead of quitting. app.quit() still closes the app fully.

    On Windows, frame: false hides the native title bar, system menu, and caption buttons. closable, minimizable, and maximizable independently control native actions when the frame is enabled. closable: false blocks the native close action, but window.close() and app.quit() remain available to backend code.

    Commands and permissions

    Registering a command is what makes backend behavior reachable from the frontend.

    app.command("ping", async () => "pong");
    javascript

    Add permission metadata with the three-argument form:

    const app = new App({
  entry: "index.html",
  permissions: {
    allow: ["fs:*", "dialog:open:settings"],
    deny: ["fs:write"]
  }
});

app.command("readConfig", { permission: "fs:read", scope: "config" }, async () => {
  return { theme: "dark" };
});
    javascript

    A plain array such as permissions: ["fs:read"] is a simple allow-list. Policy objects add deny rules, and deny always beats allow.

    • Use a group such as fs:* or dialog:* in an app policy to grant a permission family.
    • Add a scope, such as dialog:open:settings, to grant one named resource scope.
    • Commands can require several permissions at once.
    • Permission groups and wildcard scopes are accepted only in app policies, never as command requirements.
    app.command("readSettings", {
  permissions: ["fs:read:config", "dialog:open:settings"]
}, handler);
    javascript

    Individual windows can narrow the app-level policy — useful for secondary or less-trusted views. The app policy remains the maximum permission set, and a command invoked from a window must pass both policies.

    const previewWindow = app.createWindow({
  title: "Preview",
  entry: path.join(__dirname, "preview.html"),
  permissions: ["fs:read:config"]
});

    Emitting before app.run() is safe — events buffer until the bridge is ready:

    app.emit() broadcasts to every window. Use app.mainWindow.emit() or another AppWindow.emit() to target one. on(), once(), and off() exist on both App and AppWindow.

    Emitting to a closed window

    A closed window can never flush its readiness queue, so the two paths differ. app.emit() addresses whichever windows are live and skips closed ones silently. AppWindow.emit() names one specific window, so emitting at a closed one throws Window has been closed. immediately instead of queueing events that will never arrive. Check window.isClosed when a window may already be gone — a window that has not been opened yet is not closed, so it still buffers events emitted before app.run().

    Plugins

    Backend plugins register namespaced commands and events without exposing Node.js to the frontend.

    app.use({
  name: "example.settings",
  version: "1.0.0",
  permissions: ["fs:read:config"],
  setup(plugin, options) {
    plugin.command("read", { permission: "fs:read", scope: "config" },
      () => loadSettings(options.fileName));

    plugin.on("refresh", () => reloadSettings());
    return () => closeSettingsStore();
  },
  start(plugin) {
    plugin.emit("ready", { loaded: true });
  },
  stop() {
    flushSettings();
  }
}, { fileName: "settings.json" });
    javascript

    The frontend then calls NodeViewJS.invoke("example.settings:read") and works with events such as example.settings:refresh and example.settings:ready. Plugin names must be lowercase dot-or-hyphen identifiers. Setup, start, stop, and cleanup hooks are synchronous; setup is transactional and runs before app.run().

    Plugins are trusted code

    Every plugin permission must be granted by the app policy, and each plugin command can require only permissions the plugin declared. These declarations control host admission and frontend routing — they are not an operating-system sandbox. Plugins are loaded explicitly by backend code, never from the web view.

    Runtime helpers

    All helpers below are trusted backend code and are never exposed directly to the web view. Frontend access must go through a registered, permission-gated command.

    Shell

    const { App, shell } = require("nodeviewjs");

const app = new App({ entry: "index.html", permissions: ["shell:open"] });

app.command("openWebsite", { permission: "shell:open" }, ({ url }) => {
  return shell.openExternal(url);
});

app.command("showExport", { permission: "shell:open" }, ({ file }) => {
  return shell.openPath(file);
});
    javascript

    shell.openExternal(url) accepts only absolute http:, https:, and mailto: URLs without embedded credentials. shell.openPath(path) resolves the path and rejects it unless the file or directory already exists. Both return true once Windows accepts the launch request and throw a descriptive error otherwise. NodeViewJS provides no arbitrary command or shell-execution method.

    Network

    The WebView cannot reach the network — remote fetches, images, scripts, and frame content are blocked. To call an HTTP API, grant net:fetch, list the origins the app may reach, and perform the request in a command.

    const app = new App({
  entry: "index.html",
  permissions: ["net:fetch"],
  allowedOrigins: ["https://api.example.com"]
});

app.command("api:get", { permission: "net:fetch" }, async ({ path }) => {
  if (typeof path !== "string" || !path.startsWith("/")) {
    throw new TypeError("path must start with /.");
  }
  const response = await app.fetch({
    url: `https://api.example.com${path}`,
    headers: { accept: "application/json" }
  });
  if (!response.ok) throw new Error(`API returned ${response.status}`);
  return JSON.parse(response.body);
});
    javascript
    const data = await NodeViewJS.invoke("api:get", { path: "/v1/items" });
    javascript

    app.fetch() binds the app's allowlist, so a command cannot widen it. It returns { url, status, ok, headers, body } with body as text. Options are url, method, headers, body, timeoutMs, and maxResponseBytes.

    allowedOrigins takes origins only — no path, query, or fragment. Both http and https are accepted, including private and internal addresses such as http://localhost:3000 or http://192.168.1.50:8080, because listing an origin is the deliberate act that grants it. Other schemes are rejected, at most 32 entries are allowed, and an app with no allowedOrigins cannot make requests at all.

    What is validated before the request leaves the process

    ControlBehavior
    OriginMust match allowedOrigins exactly.
    RedirectsResolved manually, re-checked against the allowlist on every hop, capped at 3.
    MethodGET, HEAD, POST, PUT, PATCH, DELETE only.
    URL2048 characters maximum, no embedded credentials.
    HeadersHost, Cookie, Content-Length, and other transport headers cannot be set. Names and values are pattern-checked and length-bounded, so a value cannot inject a second header.
    Request bodyStrings only, 1 MiB maximum.
    Response8 MiB ceiling counted from bytes actually received, not a declared content-length. 30-second default timeout.
    Response headersset-cookie is stripped.

    Because net:fetch is an ordinary permission, scopes such as net:fetch:reports, the net:* group, and per-window narrowing all work unchanged.

    Two limits worth knowing

    When a command builds a request entirely from its own constants, the global fetch() is equivalent and simpler — app.fetch() earns its place when part of the request comes from the frontend. And allowedOrigins constrains code that goes through the helper; it is not a network sandbox, because backend code and plugins are trusted and can reach any host directly. The enforced boundary is net:fetch, which decides whether the WebView can cause a request at all. Allowlisting also matches the configured origin rather than the address it resolves to, so it does not defend against DNS rebinding.

    IPC helper

    The exported ipc object contains the versioned message parser, serializer, response/event constructors, validation helpers, and protocol limit constants used by the backend runtime. It accepts and returns serialized protocol data; it does not register commands or expose backend privileges. Use app.command(), app.on(), and app.emit() for application IPC — direct ipc use is for protocol adapters and tests that need the runtime's exact validation.

    Single instance, deep links, and file associations

    Single-instance applications

    Windows
    const app = new App({
  appId: "com.example.my-app",
  entry: "index.html",
  singleInstance: true
});

app.on("second-instance", ({ args, cwd }) => {
  console.log("Launched again with:", args);
  console.log("Working directory:", cwd);
});

const primary = app.run();
    javascript

    The primary app.run() returns true. A duplicate launch returns false, opens no window, forwards its arguments in the background, and exits naturally once delivery finishes.

    Do not force-exit the duplicate

    Terminating the second process immediately after app.run() interrupts argument delivery.

    The existing primary window is restored and shown before second-instance handlers run. args holds command-line values after the Node entry file, and packaged executables forward their own arguments into the same array. The stable appId identifies the instance lock, and messages are validated and limited to 64 KiB.

    Deep links and file associations

    const app = new App({

    initial is true when the URL or file started the primary process and false when it arrived from a later launch. File paths resolve to absolute paths using the launching process's working directory. Use singleInstance: true when later launches should route into the existing app.

    Custom schemes use lowercase letters, numbers, +, ., or -; file, http, https, and mailto cannot be claimed. Extensions must begin with a dot and use lowercase letters, numbers, or hyphens after normalization. Metadata is validated during development and packaging.

    Integrity verification

    The manifest records every app and runtime file's path, size, and SHA-256 digest, and is embedded byte-for-byte into the launcher. Before Node starts, the launcher rejects manifest changes, missing or extra files, reparse points, path escapes, size changes, and digest mismatches. The runtime log is the only permitted unlisted resource file.

    Secret protection

    Packaging always excludes node_modules, .git, .nodeview-webview, build, .env and .env.*, .npmrc, .pypirc, private-key and credential files (*.pem, *.key, *.pfx, *.p12, credentials.json, service-account*.json), and JavaScript source maps (*.map).

    Text inputs up to 1 MiB are scanned for common private-key, access-key, token, and credential-assignment patterns. Warnings identify only the file and pattern category — they never print the matched value.

...

  await updater.installAndRestart(app);

    Security model

    NodeViewJS deliberately avoids exposing Node.js to the frontend.

    Navigation and resource boundary

    Top-level navigation is restricted to local files inside the configured entry file's directory. Remote URLs and local files outside that directory are blocked and logged to stderr.

    On Windows, the entry directory is mapped in memory to https://app.nodeview.example/ inside that web view instance. It does not register DNS, edit the hosts file, open a port, contact a server, or persist after the web view closes. The mapping avoids Chromium's unique file: origin warnings while retaining canonical app-root checks and deny-CORS resource access.

    Windows permits web view resources only from the local app root. Remote fetches, images, scripts, and frame content receive blocked responses; popups, downloads, permission prompts, external URI schemes, and packaged DevTools are denied.

    Trusted document checks

    Windows

    window.NodeViewJS is created only in the top-level document. Native IPC verifies that each message came from the current canonical local document under the configured app root, so child frames, outside-root files, unexpected origins, and stale pages cannot invoke backend commands or emit backend events.

    IPC enforcement

    IPC requires protocol version 1 and exact message schemas. Messages are limited to 256 KiB, 32 levels, 10,000 payload nodes, and 128-character names; each window allows 64 active calls, applies a 30-second timeout, and rejects duplicate or recently replayed request IDs. Windows enforces the limits at the native forwarding boundary as well as in JavaScript.

    Known limitations

    • NodeViewJS is not an operating-system sandbox for backend code or plugins.
    • Plugins are trusted code once admitted.
    • Applications must validate command-specific payload semantics and user authorization themselves.
    • Packaged Windows applications disable DevTools.
    • WebView2 may initiate a remote frame request before cancellation, although response content is blocked — never place secrets in remote frame URLs.
    • macOS and Linux do not yet match Windows on trusted-document checks, capability lockdown, native IPC limits, package containment, integrity, and the security release gate.
    • Code signing and notarization depend on external release credentials.
    • Payloads are JSON-style data, not arbitrary JavaScript objects or Node.js values.
    • emit() is one-way and does not acknowledge completion.
    • IPC and readiness queues are deliberately bounded.

    The authoritative security limitations live in SECURITY.md; roadmap work is tracked in PLAN.md.

    Troubleshooting

    node-gyp cannot find Visual Studio

    Install Visual Studio Build Tools 2022 including the Desktop development with C++ workload. Visual Studio 2017 is not sufficient for newer Node versions — Node.js 25, for example, requires a newer supported MSVC toolchain.

    node-gyp cannot find Python

    winget install Python.Python.3.12
$env:PYTHON = "C:\Path\To\Python\python.exe"
npm run build
    powershell

    WebView2 initialization fails

    Confirm the Microsoft Edge WebView2 Runtime is installed, and that %LOCALAPPDATA%\NodeViewJS is writable — WebView2 stores its per-app profile there.

    Portable app opens and closes immediately

    Check the launcher log:

    build/portable/NodeViewDemo/resources/NodeViewDemo.log
    text

    The file is named after the app, so a renamed package writes resources/MyApp.log. Structured backend errors also go to %LOCALAPPDATA%\NodeViewJS\Logs\<app-id>-<hash>\backend.log; set NODEVIEW_LOG_PATH before launching to capture that at a known path.

    App entry file cannot be loaded

    Use an absolute or correctly resolved local file path:

    entry: path.join(__dirname, "index.html")
    javascript

    Slow startup

    Keep app startup work light before app.run(), avoid scanning large folders during launch, and lazy-load heavy data after the window is visible. Set startupTiming: true to measure.
