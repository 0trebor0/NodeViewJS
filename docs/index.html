    NodeViewJS

    A lightweight desktop runtime for building small apps with Node.js, plain HTML/CSS/JavaScript, and the operating system's own web view. Windows uses WebView2, macOS uses WKWebView, and Linux uses WebKitGTK.

    MIT Node.js 20+ Windows verified macOS / Linux pending validation v0.1.0 (untagged)

    Your frontend gets a safe window.NodeViewJS bridge; privileged work stays in registered Node.js commands. Raw Node.js APIs such as require() are never exposed to the web view.

    No Chromium bundled

    Apps use the web view already installed on the machine, so packages stay small.

    No local HTTP server

    Packaged HTML loads directly from disk through a private per-WebView mapping.

    Command-gated backend

    The frontend can only call commands you register, each behind a named permission.

    Signed updates

    Ed25519 manifests, HTTPS delivery, transactional install with rollback.

    Platform parity

    Windows is the reference platform and is verified locally. macOS and Linux compile and pass packaging/platform-boundary tests, but several security controls — trusted-document checks, capability lockdown, native IPC limits, package containment, and integrity verification — do not yet have Windows parity. Sections below are marked where a feature is Windows-only.

    Use these steps to wire NodeViewJS into an existing project instead of scaffolding a new one.

    1. Create or open your app project

    mkdir MyApp
cd MyApp
npm init -y

    2. Install NodeViewJS

    npm install github:0trebor0/NodeViewJS
    powershell

    The install builds and provides the runtime API, the nodeviewjs CLI, and the native addon and launcher. It therefore requires the native build prerequisites above, plus network access the first time the WebView2 SDK is downloaded.

    Configuration keys

    KeyPurpose
    namePortable folder name and executable name.
    appIdStable identity used for app data, notifications, and signed updates. Keep it constant across releases.
    entryYour backend NodeViewJS app entry file.
    iconOptional Windows .ico used as the window/taskbar icon and embedded in the exe.
    macIconOptional macOS .icns bundle icon.
    protocolsCustom URL schemes registered by the per-user Windows installer.
    fileAssociationsExtensions registered with Windows Open With and Default Apps.
    includeExtra project files or folders copied into resources/app.
    excludeFiles or folders removed from the app bundle.

    metadataWindows version metadata compiled into the launcher during npm run build.
    Windows path rules

    entry, icon, include, and exclude values must be relative and traversal-free. Packaging rejects inputs or destinations containing symbolic links, junctions, or other reparse-point escapes.

    No bridge script tag

    Do not add a bridge <script> to your source HTML. NodeViewJS provides window.NodeViewJS automatically. It is the only browser global; the former window.NodeView alias was removed before the first public release.

    5. Run during development

    npm run dev     # runs: nodeviewjs dev app.js
    powershell

    Dev mode enables DevTools and startup timing, and watches the entry file's directory, reloading the web view when frontend .html, .css, or .js files change. Generated folders such as node_modules, build, and .nodeview-webview are ignored.

    • Frontend reloads keep the Node.js backend process running. Restart dev mode after changing backend code.
    • Uncaught backend exceptions and promise rejections print a [NodeViewJS dev] heading with a stack trace.
    • Missing frontend entries fail before a native window opens.
    • Native web view failures show a Windows dialog and write to stderr; packaged apps capture that in resources/<AppName>.log.
    • Packaged Windows apps force DevTools off even if devtools: true is set.

    nodeviewjs dev manages NODEVIEW_DEVTOOLS, NODEVIEW_DEV_WATCH, and NODEVIEW_STARTUP_TIMING internally. Packaged apps ignore inherited values for those development defaults, so launching from a development shell cannot accidentally enable file watching or timing.

    6. Create the portable app

    npm run package     # runs: nodeviewjs package
    powershell

    1. Hello, backend

    Goal: call a Node.js function from the page and show the result. This is the whole model in miniature — the frontend never touches Node, it asks the backend to do the work.

    1. Register a command in app.js. Validate the payload: it arrives from the WebView and is untrusted, even though the page is your own code.

      const path = require("node:path");
const os = require("node:os");
const { App } = require("nodeviewjs");

const app = new App({
  title: "Tutorial",
  width: 800,
  height: 560,
  entry: path.join(__dirname, "index.html")
});

app.command("system:describe", (label) => {
  if (typeof label !== "string" || label.trim() === "") {
    throw new TypeError("label must be a non-empty string.");
  }
  return {
    label,
    platform: process.platform,
    node: process.versions.node,
    cpus: os.cpus().length
  };
});

app.run();
      javascript

    2. Call it from index.html. There is no bridge script tag — window.NodeViewJS is already there.

      <button id="go">Describe this machine</button>
<pre id="out"></pre>

<script>
  document.querySelector("#go").onclick = async () => {
    const out = document.querySelector("#out");
    try {
      const info = await NodeViewJS.invoke("system:describe", "my machine");
      out.textContent = JSON.stringify(info, null, 2);
    } catch (error) {
      out.textContent = "Failed: " + error.message;
    }
  };
</script>
      html

    3. Prove the validation runs. Change the call to NodeViewJS.invoke("system:describe", "") and click again.

    You should see Platform, Node version, and CPU count in the page. With the empty label the invoke() promise rejects and you get Failed: label must be a non-empty string. — the backend threw, and the error crossed the bridge intact.

    2. Two-way events

    Goal: push updates from the backend without the page polling, and send fire-and-forget notices back. Use invoke() when you need an answer; use events when you do not.

    1. Emit on a timer from the backend, and listen for a message from the page.

      app.on("page:opened", ({ page }) => {
  console.log("Frontend opened:", page);
});

// Safe before run(): events buffer until the bridge is ready.
app.emit("clock:tick", { at: new Date().toISOString() });

setInterval(() => {
  app.emit("clock:tick", { at: new Date().toISOString() });
}, 1000).unref();

app.run();
      javascript

    2. Subscribe in the page. on() returns an unsubscribe function and registers synchronously, so never await it.

      <p id="clock">waiting…</p>
<button id="stop">Stop listening</button>

<script>
  const unsubscribe = NodeViewJS.on("clock:tick", ({ at }) => {
    document.querySelector("#clock").textContent = at;
  });

  NodeViewJS.once("clock:tick", () => console.log("first tick only"));
  NodeViewJS.emit("page:opened", { page: "home" });

  document.querySelector("#stop").onclick = () => unsubscribe();
</script>
      html
    You should see The timestamp updating once a second, Frontend opened: home in your terminal, and first tick only once in DevTools. Clicking Stop freezes the clock while the backend keeps emitting — the events still arrive and are simply discarded.

    3. Permissions

    Goal: gate commands behind named permissions, and watch a deny rule beat a wildcard allow.

    1. Give the app a policy with both an allow and a deny rule.

      const app = new App({
  entry: path.join(__dirname, "index.html"),
  permissions: {
    allow: ["fs:*", "clipboard:read"],
    deny: ["fs:write"]
  }
});

app.command("notes:read",  { permission: "fs:read",  scope: "notes" }, () => "the notes");
app.command("notes:write", { permission: "fs:write", scope: "notes" }, () => "saved");
      javascript

    2. Call both from the page.

      for (const name of ["notes:read", "notes:write"]) {
  try {
    console.log(name, "=>", await NodeViewJS.invoke(name));
  } catch (error) {
    console.log(name, "=> refused:", error.message);
  }
}
      javascript
    You should see notes:read returns, and notes:write is refused even though fs:* was allowed — deny always beats allow. Permissions are checked when the command runs, not when it is registered, so registration never throws for a missing grant.

    4. A second window

    Goal: open an independent window with its own page and a narrower permission policy, then send an event to just that window.

    1. Create it. Unspecified options inherit from the main window.

  title: "Settings",
  width: 520,
  height: 420,
  entry: path.join(__dirname, "settings.html"),
  permissions: ["clipboard:read"]
});

settings.on("settings:saved", (value) => console.log("saved", value));

app.run();
      javascript

    2. Target one window, or broadcast to all of them.

      settings.emit("theme:changed", { theme: "dark" });  // this window only
app.emit("theme:changed", { theme: "dark" });       // every open window
      javascript
    You should see Two native windows, each with its own WebView and IPC channel. A command invoked from settings.html must satisfy both the app policy and that window's narrower one — the app policy is always the maximum grant.

    5. Window lifecycle

    Goal: observe the four window states, flush state on shutdown, and understand why a closed window sometimes disappears from app.windows and sometimes does not.

    1. Read lifecycleState as a window moves through its life.

      const preview = app.createWindow({
  title: "Preview",
  entry: path.join(__dirname, "preview.html")
});

console.log(preview.lifecycleState);   // "configured" - created, never opened

app.run();
console.log(preview.lifecycleState);   // "open"

preview.close();
console.log(preview.lifecycleState);   // "disposed" - closed while running
console.log(app.windows.includes(preview)); // false
      javascript

    2. Flush state before the app exits. before-quit is synchronous — a promise you return is reported but not awaited, so do the work inline or in a plugin stop hook.

      app.on("before-quit", ({ windows }) => {
  console.log("closing with", windows, "window(s) open");
  saveEverythingSynchronously();
});
      javascript

    3. Guard an emit when a window may already be gone.

      if (!preview.isClosed) {
  preview.emit("refresh");
}
      javascript
    You should see configured, then open, then disposed. Emitting at a disposed window throws rather than queueing events nothing will ever deliver. A window closed before run() becomes closed instead and stays in app.windows, because a failed startup can be retried and reopen it.

    6. Custom title bar

    Windows 10 and 11

    Goal: replace the native title bar with your own HTML and CSS, and wire the window controls through permission-gated commands.

    1. Turn off the native frame and expose the three controls the page needs.

      const app = new App({
  entry: path.join(__dirname, "index.html"),
  frame: false
});

const control = { permission: "window:control" };

app.command("window:startDrag", control, () => { app.mainWindow.startDrag(); return true; });
app.command("window:minimize",  control, () => { app.mainWindow.minimize();  return true; });
app.command("window:close",     control, () => {
  // Let the IPC response finish before the window is destroyed.
  setImmediate(() => app.mainWindow.close());
  return true;
});

app.run();
      javascript

    2. Build the bar. pointerdown anywhere but a button starts a native drag.

      <style>
  html, body { margin: 0; }
  .titlebar {
    height: 36px; display: flex; align-items: center;
    background: #162033; color: #fff; user-select: none;
  }
  .titlebar-title { flex: 1; padding-left: 12px; font: 13px system-ui; }
  .titlebar button { width: 46px; height: 36px; border: 0; background: transparent; color: inherit; }
  .titlebar button:hover { background: #2b3b58; }
  .titlebar .close:hover { background: #c42b1c; }
</style>

<header class="titlebar">
  <span class="titlebar-title">My App</span>
  <button id="min" aria-label="Minimize">&#x2212;</button>
  <button id="close" class="close" aria-label="Close">&#x2715;</button>
</header>

<script>
  document.querySelector(".titlebar").addEventListener("pointerdown", (event) => {
    if (event.target.closest("button")) return;
    NodeViewJS.invoke("window:startDrag");
  });
  document.querySelector("#min").onclick   = () => NodeViewJS.invoke("window:minimize");
  document.querySelector("#close").onclick = () => NodeViewJS.invoke("window:close");
</script>
      html
    You should see A frameless window you can drag by its bar, minimize, and close. If closing feels flaky, check that setImmediate() is still wrapping close() — without it the window can be destroyed before the reply is sent.

    7. Menus

    Goal: add an application menu and a right-click context menu. Menu templates are data, not callbacks — items carry string IDs and emit a backend event.

    1. Describe the menu and handle its events. One menu handler serves both the application menu and context menus.

      const app = new App({
  entry: path.join(__dirname, "index.html"),
  menu: [
    {
      label: "File",
      submenu: [
        { id: "file.open", label: "Open", accelerator: "Ctrl+O" },
        { type: "separator" },
        { id: "file.autosave", label: "Auto save", type: "checkbox", checked: true }
      ]
    }
  ]
});

app.on("menu", ({ id, checked, window }) => {
  if (id === "file.open") console.log("Open, from window", window.id);
  if (id === "file.autosave") console.log("Auto save:", checked);
});
      javascript

    2. Show a context menu. Native menu APIs are backend-only, so route the page's request through a window:control command.

      app.command("menu:context", { permission: "window:control" }, ({ x, y }) => {
  app.mainWindow.showContextMenu([
    { id: "edit.copy", label: "Copy", accelerator: "Ctrl+C" },
    { id: "edit.delete", label: "Delete" }
  ], { x, y });
  return true;
});
      javascript
      window.addEventListener("contextmenu", (event) => {
  event.preventDefault();
  NodeViewJS.invoke("menu:context", { x: event.clientX, y: event.clientY });
});
      javascript

    3. Swap the menu at runtime with app.setMenu(template), or remove it with app.setMenu(null).

    You should see A File menu with a working Ctrl+O accelerator and a checkbox that reports its new state. Templates are capped at 256 items and eight levels, and IDs and accelerators must be unique — a duplicate throws when you build the menu, not silently later.

    Goal: keep the app alive in the tray when the window is closed, with a custom tray menu.

    1. Set closeToHide so the close button hides instead of quitting, and give the tray a menu.

    9. Taskbar feedback

    Windows

    2. Add an overlay badge. It must be an existing .ico file.

      app.setTaskbarOverlay("assets/badge.ico", "3 unread");

    1. Set a stable appId and title — Windows caches notification identity against them, so keep both constant across releases.

app.run();
app.showNotification({ title: "My App", message: "Finished loading." });
      javascript

    2. Let the page request one through a narrow command rather than exposing the helper.

      app.command("notify", { permission: "notification:show" }, ({ title, message }) => {
  app.showNotification({ title, message });

    11. Dialogs and clipboard

    Goal: ask the user to pick a file and copy text, both through permission-gated commands. These helpers are backend-only by design.

    1. Wire up the dialog helpers. They return an absolute path, or null when the user cancels — always handle the cancel.

      const { App, dialog, clipboard } = require("nodeviewjs");

const app = new App({
  entry: path.join(__dirname, "index.html"),
  permissions: ["dialog:open", "dialog:save", "clipboard:*"]
});

app.command("file:pick", { permission: "dialog:open" }, () => {
  const selected = dialog.openFile();
  if (selected === null) return { cancelled: true };
  return { cancelled: false, path: selected };
});
      javascript

    2. Add clipboard access. Null characters are rejected, because the Windows clipboard text format is null-terminated.

      app.command("clip:copy", { permission: "clipboard:write" }, ({ text }) => {
  if (typeof text !== "string") throw new TypeError("text must be a string.");
  return clipboard.writeText(text);
});

app.command("clip:paste", { permission: "clipboard:read" }, () => clipboard.readText());
      javascript
    You should see A native file picker, and text moving in and out of the system clipboard. clipboard.readText() returns an empty string when the clipboard holds something that is not text — not an error, so check for "".

    12. Saving settings

    Goal: persist user preferences to the per-user application data directory, and survive a first run where the file does not exist yet.

    1. Read with defaults. A missing file is not an error — you get the defaults back.

      const { config } = require("nodeviewjs");

const FILE = { appName: "MyApp", fileName: "settings.json" };

app.command("settings:load", async () => {
  return config.read({ ...FILE, defaults: { theme: "light", zoom: 1 } });
});
      javascript

    2. Write it back, validating first. The payload came from the page.

      const THEMES = new Set(["light", "dark"]);

app.command("settings:save", async ({ theme, zoom }) => {
  if (!THEMES.has(theme)) throw new TypeError("Unknown theme.");
  if (typeof zoom !== "number" || !(zoom >= 0.5 && zoom <= 3)) {
    throw new RangeError("zoom must be between 0.5 and 3.");
  }
  await config.write({ ...FILE, data: { theme, zoom } });
  app.emit("settings:changed", { theme, zoom });
  return true;
});
      javascript
    You should see Settings surviving a restart, stored under the user's app-data directory rather than beside the executable. File names must be a plain .json name — no directories, no traversal, 255 characters maximum — so a caller cannot steer the write somewhere else.

    13. Calling an API

    Goal: reach an HTTP API from the page. The WebView itself cannot touch the network, so the backend makes the request on its behalf.

    1. Grant net:fetch and list the origins the app may reach. With no allowedOrigins, no request can be made at all.

      const app = new App({
  entry: path.join(__dirname, "index.html"),
  permissions: ["net:fetch"],
  allowedOrigins: ["https://api.github.com"]
});
      javascript

    2. Expose a command that controls the shape of the URL. Never let the frontend supply the host — give it only the part it needs, and validate that.

      app.command("gh:repo", { permission: "net:fetch" }, async ({ owner, name }) => {
  const SEGMENT = /^[A-Za-z0-9._-]{1,100}$/;
  if (!SEGMENT.test(owner ?? "") || !SEGMENT.test(name ?? "")) {
    throw new TypeError("owner and name must be simple path segments.");
  }
  const response = await app.fetch({
    url: `https://api.github.com/repos/${owner}/${name}`,
    headers: { accept: "application/vnd.github+json" }
  });
  if (!response.ok) throw new Error(`GitHub returned ${response.status}`);
  const repo = JSON.parse(response.body);
  return { stars: repo.stargazers_count, description: repo.description };
});
      javascript

    3. Call it, then try to break out by asking for a different host.

      console.log(await NodeViewJS.invoke("gh:repo", { owner: "0trebor0", name: "NodeViewJS" }));

// The regex refuses this before any request is made.
await NodeViewJS.invoke("gh:repo", { owner: "../..", name: "x" });
      javascript
    You should see Star count and description in the page, and a rejection for the traversal attempt. app.fetch() binds the app's allowlist, so a command cannot widen it; redirects are re-checked on every hop, and Host and Cookie headers cannot be set by the caller. When a command builds a URL entirely from its own constants, the global fetch() is equivalent and simpler.

    14. Writing a plugin

    Goal: package a feature as a plugin with namespaced commands and events, so it can be dropped into another app without touching that app's wiring.

    1. Write the plugin. Every hook is optional; setup may return a cleanup function, and it runs before app.run().

      const counterPlugin = {
  name: "example.counter",
  version: "1.0.0",
  permissions: ["fs:read:counter"],
  setup(plugin, options) {
    let count = options.start ?? 0;

    plugin.command("increment", { permission: "fs:read", scope: "counter" }, () => ++count);
    plugin.command("value", () => count);
    plugin.on("reset", () => { count = options.start ?? 0; });

    return () => console.log("counter cleaned up");
  },
  start(plugin) {
    plugin.emit("ready", { start: 0 });
  },
  stop() {
    console.log("counter stopping");
  }
};
      javascript

    2. Register it. The app policy must already grant every permission the plugin declares.

  entry: path.join(__dirname, "index.html"),
  permissions: ["fs:read:counter"]
});

app.run();

    3. Call it from the page. Everything is namespaced under the plugin name.

await NodeViewJS.invoke("example.counter:value");     // 11

      javascript

    Supported payloads and limits

    Payloads and results support JSON-style data only: null, booleans, finite numbers, strings (including Unicode), arrays, and plain objects.

    Unsupported: functions, symbols, BigInt, NaN, infinity, DOM elements, cyclic objects, class instances, streams, and native Node.js objects. Convert these to plain data first.

    LimitValue
    Message size256 KiB
    Nesting depth32 levels
    Payload nodes10,000
    Command / event name length128 characters
    Pending calls per window64
    Request timeout30 seconds
    Readiness queue per direction1,024 events or 1 MiB per window

  const response = await app.fetch({
    url: `https://api.example.com${path}`,
    headers: { accept: "application/json" }
  });
  if (!response.ok) throw new Error(`API returned ${response.status}`);
  return JSON.parse(response.body);
});

    const data = await NodeViewJS.invoke("api:get", { path: "/v1/items" });
    javascript

    app.fetch() binds the app's allowlist, so a command cannot widen it. It returns { url, status, ok, headers, body } with body as text. Options are url, method, headers, body, timeoutMs, and maxResponseBytes.

    allowedOrigins takes origins only — no path, query, or fragment. Both http and https are accepted, including private and internal addresses such as http://localhost:3000 or http://192.168.1.50:8080, because listing an origin is the deliberate act that grants it. Other schemes are rejected, at most 32 entries are allowed, and an app with no allowedOrigins cannot make requests at all.

    What is validated before the request leaves the process

    ControlBehavior
    OriginMust match allowedOrigins exactly.
    RedirectsResolved manually, re-checked against the allowlist on every hop, capped at 3.
    MethodGET, HEAD, POST, PUT, PATCH, DELETE only.
    URL2048 characters maximum, no embedded credentials.
    HeadersHost, Cookie, Content-Length, and other transport headers cannot be set. Names and values are pattern-checked and length-bounded, so a value cannot inject a second header.
    Request bodyStrings only, 1 MiB maximum.
    Response8 MiB ceiling counted from bytes actually received, not a declared content-length. 30-second default timeout.
    Response headersset-cookie is stripped.

    Because net:fetch is an ordinary permission, scopes such as net:fetch:reports, the net:* group, and per-window narrowing all work unchanged.

    Two limits worth knowing

    When a command builds a request entirely from its own constants, the global fetch() is equivalent and simpler — app.fetch() earns its place when part of the request comes from the frontend. And allowedOrigins constrains code that goes through the helper; it is not a network sandbox, because backend code and plugins are trusted and can reach any host directly. The enforced boundary is net:fetch, which decides whether the WebView can cause a request at all. Allowlisting also matches the configured origin rather than the address it resolves to, so it does not defend against DNS rebinding.

    Navigation and resource boundary

    Top-level navigation is restricted to local files inside the configured entry file's directory. Remote URLs and local files outside that directory are blocked and logged to stderr.

    On Windows, the entry directory is mapped in memory to https://app.nodeview.example/ inside that web view instance. It does not register DNS, edit the hosts file, open a port, contact a server, or persist after the web view closes. The mapping avoids Chromium's unique file: origin warnings while retaining canonical app-root checks and deny-CORS resource access.

    Windows permits web view resources only from the local app root. Remote fetches, images, scripts, and frame content receive blocked responses; popups, downloads, permission prompts, external URI schemes, and packaged DevTools are denied.

    Trusted document checks

    Windows

    window.NodeViewJS is created only in the top-level document. Native IPC verifies that each message came from the current canonical local document under the configured app root, so child frames, outside-root files, unexpected origins, and stale pages cannot invoke backend commands or emit backend events.

    IPC enforcement

    IPC requires protocol version 1 and exact message schemas. Messages are limited to 256 KiB, 32 levels, 10,000 payload nodes, and 128-character names; each window allows 64 active calls, applies a 30-second timeout, and rejects duplicate or recently replayed request IDs. Windows enforces the limits at the native forwarding boundary as well as in JavaScript.

    Known limitations

    • NodeViewJS is not an operating-system sandbox for backend code or plugins.
    • Plugins are trusted code once admitted.
    • Applications must validate command-specific payload semantics and user authorization themselves.
    • Packaged Windows applications disable DevTools.
    • WebView2 may initiate a remote frame request before cancellation, although response content is blocked — never place secrets in remote frame URLs.
    • macOS and Linux do not yet match Windows on trusted-document checks, capability lockdown, native IPC limits, package containment, integrity, and the security release gate.
    • Code signing and notarization depend on external release credentials.
    • Payloads are JSON-style data, not arbitrary JavaScript objects or Node.js values.
    • emit() is one-way and does not acknowledge completion.
    • IPC and readiness queues are deliberately bounded.

    The authoritative security limitations live in SECURITY.md; roadmap work is tracked in PLAN.md.
