# Changelog

## Unreleased

### Added

- `docs/index.html` gains a Tutorials section: eighteen task-shaped walkthroughs covering commands, events, permissions, multiple windows, the window lifecycle, custom title bars, menus, tray, taskbar, notifications, dialogs and clipboard, settings persistence, network access, plugins, deep links, packaging, signed updates, and debugging. Each states a goal, numbered steps, and the observable result, so a reader can confirm the feature works rather than only read about it.

- Two further dogfood applications, completing the three shapes the API is tested against: `examples/digest` is a single-window utility that grants no permissions at all, and `examples/focus` is a plugin-based focus timer using the tray, taskbar progress, notifications, single-instance launch, and a `focus://` deep link. `npm run test:example-shapes` drives both through the IPC layer, including a deep link routed through the real startup path.
- `wiki/API-Findings.md` records what building those applications surfaced about the API itself: there is no backend-side event bus, backend code cannot invoke a registered command, accelerators reject punctuation keys, synchronous shutdown shapes how applications persist, and the testable application structure is not the one the API suggests. Recorded rather than acted on, because changing the API under the applications testing it would waste the exercise.
- `examples/tasks` is a small real desktop application used to dogfood the API rather than to demonstrate features: a task list and a separate quick-add window kept in sync by broadcast events, a quick-add window whose permission policy narrows the app's so it can add a task but not read the list, validated commands, persistence through the config helper, a menu and tray that raise events rather than running privileged code, and a real updater wiring that activates only when the release environment is configured. `npm run example:tasks` runs it, and `npm run test:example-tasks` drives its backend through the IPC layer as an integration test.
- `npm run test:limits` drives valid-but-hostile workloads — ten thousand commands, ten thousand events, repeated maximum-size messages, a full window of never-finishing handlers, a page that never becomes ready, and five hundred windows opening and closing under traffic — and asserts that the runtime's own bookkeeping stays bounded. With `--expose-gc` it also asserts the heap does not grow with the traffic.
- `npm run test:updater-failures` injects a failure at every stage of an update: a manifest signed by the wrong key or modified after signing, a partial, interrupted, corrupted, or mis-sized download, a staged installer altered or deleted after verification, and a helper process that cannot start. The guarantee asserted throughout is that an unsuccessful update leaves the working installation untouched and never hands the machine over.
- `app.on("before-quit", handler)` fires at the start of shutdown, and `app.isQuitting` reports whether shutdown has begun. Shutdown is synchronous, so a handler must do its work synchronously.
- `examples/basic` is now the canonical starter application, and `nodeviewjs create` generates that same app rather than a second, simpler one. It exercises the recommended architecture in one place: window creation, a declared permission policy, one validated backend command per privileged operation, a backend-to-frontend event, a native menu, packaging configuration, error handling, and a commented update stub. The CLI generates it by retargeting the example at the installed package, and the CLI test fails if the two drift.
- Installing NodeViewJS now prefers a published prebuilt native binary over a local compile, so `npm install nodeviewjs` need not require a C++ toolchain. Expected SHA-256 digests ship inside the package in `native-checksums.json` and are never read from the download host, the host must be `https` without credentials, and redirects are refused. A missing, unreachable, oversized, or unpublished artifact falls back to a source build; a digest mismatch fails the install instead of silently compiling, and nothing is written unless every file for the target verifies first. Set `NODEVIEW_BUILD_FROM_SOURCE=1` to force a compile. No binaries are published yet, so every install still builds from source and behaviour is unchanged until they are. Maintainers record digests with `npm run native:checksums`.
- `nodeviewjs doctor` reports whether this machine can build, run, and package an app: Node.js version, whether the native addon is present and loadable, Python 3 for `node-gyp`, the platform C++ toolchain, the system WebView runtime, and packaging prerequisites. Each failure names the install command that fixes it, and the command exits non-zero when a required check fails so it can gate a script. `--signing` adds the release signing prerequisites, which stay off the default report; `--json` prints machine-readable output.
- TypeScript declarations for the whole public API ship with the package (`types/index.d.ts`, `types/ipc.d.ts`) and are wired into `package.json`, so editors type `App`, `AppWindow`, `Updater`, the runtime helpers, options, events, and payloads without any extra install. `types/bridge.d.ts` declares the frontend `NodeViewJS` global. `npm run test:types` type-checks a usage file against them.
- `package.json` declares an explicit `exports` map. `nodeviewjs` resolves the public API and `nodeviewjs/ipc` the advanced protocol helpers; every other internal runtime file is no longer importable through a deep path. `npm run test:exports` verifies resolution from an installed package.
- `AppWindow.lifecycleState` reports `configured`, `open`, `closed`, or `disposed`.
- `npm run test:tarball` installs the packed npm tarball into a clean project and checks that the public entry points, type declarations, and CLI resolve there.
- CI now runs the Windows job on Node 20 as well as Node 22 — 20 is the minimum version `package.json` supports — and adds a Node 20 job that packs the artifact and runs the export, type, and tarball-install checks.
- `wiki/Lifecycle.md` documents startup and shutdown order, the window state table, handler attachment, and what happens when a callback throws.
- `npm run test:rc` is a release-candidate gate that runs against the package as it would be published: it packs the tarball, installs it into a clean project, generates an application with the installed CLI, runs it so a real window opens, exercises frontend-to-backend IPC through a permission-gated command and backend-to-frontend events acknowledged by the page, checks the process exits cleanly, packages that application with the installed CLI, verifies every entry in the packaged integrity manifest by recomputing its size and digest, and verifies signed update metadata including that a tampered manifest is refused. `npm run test:full` ends with it. Set `NODEVIEW_RC_BUILD=1` to compile the addon inside the temporary project rather than staging this repository's build.
- `npm run test:fuzz` applies seeded, structure-aware malformed input to the validators on each trust boundary — IPC parsing and serialization, permission policies, protocol and file-association manifests, launch arguments, menu and tray templates, update metadata, package integrity manifests, the network origin allowlist, and the whole inbound frontend message path. It asserts four properties: the call always returns or throws, a rejection is always a real `Error` with a bounded message, no input can reach `Object.prototype` or `Array.prototype`, and anything accepted satisfies that validator's contract. The seed is printed and can be pinned with `NODEVIEW_FUZZ_SEED` to reproduce a failure. It runs as part of `npm test` and the security gate.
- Backend commands can call HTTP APIs through `app.fetch()` and the exported `net` helper, gated by a new `net:fetch` permission and an `allowedOrigins` application option. The WebView itself stays sandboxed; only the backend performs the request. Both `http` and `https` origins are accepted, including private and internal addresses, because listing an origin is the deliberate act that grants it; other schemes are rejected, and an app with no `allowedOrigins` cannot make requests. Requests are validated before they leave the process: method and header allowlists, a 2048-character URL limit, no credentials in the URL, a 1 MiB request body limit, an 8 MiB response ceiling counted from the bytes actually received, and a 30-second default timeout. Redirects are re-checked against the allowlist on every hop and capped at three, so an allowed origin cannot hand the request to another host, and `set-cookie` is stripped from responses.
- `setup.bat` installs missing Windows prerequisites through `winget` and then runs `npm install`. It checks Node.js 20 or newer, Python 3, the Visual Studio 2022 Desktop development with C++ workload, and the Microsoft Edge WebView2 Runtime, installing only what is absent. `/check` reports status without changing anything and `/deps` skips the project install.
- `AppWindow.isClosed` reports whether a window has been closed. It is distinct from `!isOpen`: a window that has not been opened yet is not closed, so it still buffers events emitted before `app.run()`.
- `npm run test:native`, `npm run test:native-ui`, and `npm run test:full` group the native and WebView suites that previously had no aggregate runner.
- `docs/index.html` is a complete single-page project guide covering setup, CLI, the frontend bridge, the backend API, packaging, updates, security, and troubleshooting.

### Removed

- The `window.NodeView` compatibility alias. `window.NodeViewJS` is the only browser global. Applications that used the alias must switch to `window.NodeViewJS`.

### Fixed

- Frontend listeners are isolated from one another. A `NodeViewJS.on()` listener that threw stopped every listener registered after it from seeing the event, and the failure escaped into the transport callback; a listener that returned a rejecting promise became an unhandled rejection in the page. Failures are now reported to the page console and the remaining listeners still run.
- `app.quit()` now shuts down in a fixed, documented order: stop new work, notify the application, notify plugins, close windows, release IPC state, release native and process resources. Previously new windows could still be opened and new frontend messages still processed while shutdown was under way. Calling `quit()` again is a no-op, and a failure in one phase no longer prevents the later phases from releasing resources.
- A command that finishes after its window closed, or after the app quit, no longer throws out of the native callback while trying to deliver a response nobody can receive. The answer is dropped instead.
- A window whose native creation fails is no longer left in `app.windows`. `createWindow()` registered it before opening it, so a failure before the native window existed left a phantom entry reporting itself as one of the app's windows.
- The native host no longer retains closed windows. `NodeViewJSRuntime` kept every `NativeWindow` it ever created for the life of the process: `OnWindowDestroyed` removed the id from the live set but never released the object, because it runs from inside that window's own `WM_DESTROY` handling, where freeing it would pull the object out from under the code still executing. Destroyed windows are now queued and released by the next message-pump tick, which never runs nested inside a window procedure. Closing an already released window stays a no-op rather than becoming an error. This completes the window lifecycle work: the JavaScript side stopped retaining closed windows in `app.windows`, and the native side now matches.
- Native callbacks no longer leak unhandled promise rejections. The window message handler started an async dispatch whose rejection had no consumer, so a failing frontend event handler surfaced as an unhandled rejection instead of a reported error. Every promise started from a native callback is now consumed inside the runtime.
- Application and window event handler failures are now isolated. A handler that throws or rejects is reported to the backend log and the remaining handlers still run; previously the first failure aborted the rest of the dispatch for that event. Command handlers are unchanged: their failures are still returned to the frontend, where `invoke()` rejects.
- Windows closed while the app is running are removed from `app.windows` and their event handlers and buffered messages are released. A long-running app that opened a transient window per document previously retained every one of them for the life of the process. Windows closed before `app.run()` still stay listed so a failed startup can retry them.
- The unsubscribe function returned by `on()` and `once()` now runs the same cleanup as `off()`, on `App`, `AppWindow`, and the frontend bridge. It previously removed the handler but left an empty entry behind for that event name, so subscribing and unsubscribing many distinct names grew the internal maps without bound. Calling it more than once is harmless.
- `app.emit()` no longer queues broadcasts into closed windows. A closed window can never flush its readiness buffer, so events accumulated there until the buffer limit threw out of `app.emit()` and broke app-wide events for the remaining open windows.
- `AppWindow.emit()` on a closed window now throws `Window has been closed.` immediately instead of queueing events that can never be delivered. `app.emit()` continues to broadcast to the open windows and skips closed ones.
- `notification.show()` validates its options before loading the native addon. Invalid arguments previously surfaced as a native addon load failure on machines where the addon had not been built.
- `config.resolveConfigPath()` rejects file names longer than 255 characters. An over-long name previously reached the filesystem and failed as `ENOENT`, which reads as a missing directory rather than an over-long file name.

### Security

- Sparse arrays no longer bypass validation. `Array.prototype.map` skips holes, so an array such as `new Array(4)` or `["a", , "b"]` walked straight through the per-item validators with its items never checked, and the unvalidated result reached the permission policy, the network origin allowlist, protocol and file-association manifests, and menu templates. Every one of those boundaries now rejects an array containing an empty item. Found by the new fuzz suite; each fix has a pinned regression test.
- Validation errors no longer quote a rejected value without bound. Permission entries, protocol and file-association options, menu items and accelerators, window colors, taskbar states and icon paths, and update manifest fields were interpolated into the error message at full length, which put attacker- or server-controlled content of arbitrary size into the message and the backend log. Quotes are now truncated to 120 characters with the original length appended. The update manifest path matters most because its fields arrive from a remote server.

- `undici` is pinned to 6.28.0 through a dependency override. The version `node-gyp` resolved carried advisories for response desynchronization, CRLF injection, and cookie attribute injection.

### Changed

- The native addon is now built against a pinned N-API version (`NAPI_VERSION=8`) instead of whichever version the build machine's Node headers offered. Without the pin, a binary built on a current Node could call symbols an older supported Node does not export, which would have meant one prebuilt artifact per Node major rather than one per platform. N-API 8 is available in every Node.js release this package supports. `npm run test:napi` checks the pin, and fails if the addon starts referencing an N-API symbol outside the set it is known to use.
- Runtime errors developers actually hit now explain themselves in the backend log, while the message delivered to the page stays terse. An unknown command records what was invoked, how to register it, and which commands *are* registered, which usually identifies a typo at once. A denied command records whether the app policy or the window's narrowed policy refused it, the window's effective allow and deny lists, and the option to change. A message that fails IPC schema validation is still dropped without a reply, but is now recorded with a bounded quote instead of vanishing silently — rate limited to five reports per application so a hostile page cannot flood the log. Nothing new is sent over IPC: guidance would otherwise describe backend configuration to an untrusted page.
- A WebView2 startup failure now explains itself instead of showing a bare `HRESULT`. A missing runtime, a profile already in use by another instance, and a denied data directory are each recognised and answered with the command or change that fixes them; anything else points at `npx nodeviewjs doctor`.
- A packaged application that fails its integrity check now tells whoever is running it what happened and how to recover — that the files no longer match the ones published, that this usually means modification, corruption, or antivirus quarantine, and to reinstall from the original download — instead of only naming the failing file.
- A missing or unloadable native addon now explains itself: where it was searched for, that `npx nodeviewjs doctor` reports the missing prerequisite, and how to rebuild. A Node.js version mismatch is detected specifically and answered with the rebuild instruction rather than a raw `NODE_MODULE_VERSION` error.
- A failed update signature check now states that the manifest is well formed but was not signed by the key the app trusts, and what to do about it.
- The root `README.md` is now an onboarding document: positioning, install, a runnable example, a platform maturity table, a feature summary, a security summary, and links. The reference material it carried moved into the wiki pages for getting started, the backend API, the frontend bridge, packaging, security, and testing, where it is now more complete.
- Windows native build and packaging now fail early with a clear Python 3 prerequisite message before `node-gyp` runs.
- Command permissions can now be narrowed per window while the app-level permission policy remains the maximum grant.
- Documentation now shows backend error log locations and keeps generated starter and packaged demo `greet` examples aligned on the string payload API.
- Packaged apps now ignore inherited CLI development flags for DevTools, file watching, and startup timing defaults; explicit application options remain authoritative.
- Windows local app pages now use a private, per-WebView `https://app.nodeview.example/` mapping instead of direct `file:` navigation. The mapping exists only in memory for the lifetime of the WebView, performs no network or global system configuration, retains canonical app-root security checks, and removes Chromium unique-file-origin console warnings.
- Windows WebView2 profile directories now use explicit Win32 directory creation so access failures are reported instead of terminating the process; live bridge diagnostics use isolated temporary profile roots that are removed after each child test exits.
- Windows tray icons can now use validated custom menus with commands, checkboxes, separators, disabled items, submenus, and dedicated `tray-menu` events. The built-in Show/Quit menu remains the default.
- Windows notifications now register the app title against its per-user AppUserModelID and use the AUMID-addressed Windows toast API instead of inheriting `Node.js JavaScript Runtime` from the legacy host-process balloon.
- Windows 11 apps can configure native title-bar, title-text, and border colors at startup or runtime through `windowColors` and `setWindowColors()`; state reports whether the OS supports native chrome colors.
